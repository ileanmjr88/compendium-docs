STM32CubeMX genera el andamiaje del proyecto. Compendium fija el compilador,
las herramientas de build y el flasher. El preset de CMake que escribe
CubeMX ya funciona; usted solo provee el toolchain.

```bash
compendium install
source <(compendium activate)
cmake --preset Debug
cmake --build build/Debug
openocd -f interface/stlink.cfg -f target/stm32l4x.cfg \
  -c "program build/Debug/nucleo_l432kc_first.elf verify reset exit"
```

Esta guía recorre cómo Compendium encaja en un proyecto generado por
CubeMX, qué exporta activate para builds embebidos, y los detalles que
conviene conocer.

## Generar el andamiaje con CubeMX

Antes de que Compendium pueda hacer algo, necesita un proyecto de CubeMX.
Desde STM32CubeMX:

1. Cree o abra un archivo `.ioc`. Configure el árbol de reloj, los periféricos y los pines.
2. Project Manager → Toolchain/IDE → **CMake**.
3. Project Manager → Code Generator → marque **Generate peripheral initialization as a pair of '.c/.h'**.
4. **Generate Code**.

CubeMX escribe:

```
nucleo_l432kc_first/
├── nucleo_l432kc_first.ioc    # proyecto de CubeMX
├── CMakeLists.txt             # CMake de nivel superior
├── CMakePresets.json          # presets Debug + Release
├── cmake/
│   ├── gcc-arm-none-eabi.cmake   # archivo de toolchain (los flags del MCU viven aquí)
│   └── stm32cubemx/              # targets HAL/CMSIS generados
├── Core/                      # main.c, handles del HAL, stm32xx_it.c
├── Drivers/                   # fuentes del HAL de STM32 + CMSIS
├── startup_stm32l432xx.s      # tabla de vectores + manejador de reset
└── STM32L432XX_FLASH.ld       # linker script
```

Compendium se conecta a esto sin cambiar nada.

## Añadir `compendium.toml`

El único archivo que Compendium necesita:

```toml
[compendium]
name = "nucleo_l432kc_first"
version = "0.1.0"
min_compendium = "0.1.0"

[registry]
source = "public"

[languages]
cpp = "arm-none-eabi-gcc@14.2.1-1.1"

[tools]
cmake = "4.3.1"
ninja = "1.13.2"
openocd = "0.12.0-7"
```

La clave `cpp` maneja tanto C como C++; `arm-none-eabi-gcc` incluye ambos
drivers. Los proyectos de CubeMX son normalmente C + ASM, pero el mismo
compilador cubre C++ si lo añade más adelante.

`compendium install` extrae el compilador cruzado a
`~/.local/compendium/languages/arm-none-eabi-gcc/14.2.1-1.1/`, y OpenOCD a
`~/.local/compendium/tools/openocd/0.12.0-7/`. Ambos quedan en el `PATH`
cuando activa.

## Qué puso CubeMX en el archivo de toolchain de CMake

Abra `cmake/gcc-arm-none-eabi.cmake`. CubeMX escribió aquí los flags
específicos del MCU:

```cmake
set(CMAKE_SYSTEM_NAME           Generic)
set(CMAKE_SYSTEM_PROCESSOR      arm)

set(TOOLCHAIN_PREFIX            arm-none-eabi-)
set(CMAKE_C_COMPILER            ${TOOLCHAIN_PREFIX}gcc)
set(CMAKE_CXX_COMPILER          ${TOOLCHAIN_PREFIX}g++)
set(CMAKE_ASM_COMPILER          ${CMAKE_C_COMPILER})
set(CMAKE_LINKER                ${TOOLCHAIN_PREFIX}g++)
set(CMAKE_OBJCOPY               ${TOOLCHAIN_PREFIX}objcopy)
set(CMAKE_SIZE                  ${TOOLCHAIN_PREFIX}size)

set(TARGET_FLAGS "-mcpu=cortex-m4 -mfpu=fpv4-sp-d16 -mfloat-abi=hard ")

# ...linker script, gc-sections, --specs=nano.specs, etc.
```

Dos cosas a notar:

1. El archivo de toolchain usa el **prefijo** `arm-none-eabi-` y deja que
   el shell resuelva esos binarios en el `PATH`. No hardcodea una ruta. Ese
   es el contrato que Compendium cumple: después de activate, `which
   arm-none-eabi-gcc` resuelve a la copia gestionada por Compendium.
2. Los flags del MCU (`-mcpu`, `-mfpu`, `-mfloat-abi`), el linker script y
   `--specs=nano.specs` viven todos en este archivo, no en
   `compendium.toml`. Compendium no gestiona estos. Distintas placas
   necesitan distintos flags aquí.

El `CMakePresets.json` que escribió CubeMX apunta a este archivo de
toolchain:

```json
{
  "version": 3,
  "configurePresets": [
    {
      "name": "default",
      "hidden": true,
      "generator": "Ninja",
      "binaryDir": "${sourceDir}/build/${presetName}",
      "toolchainFile": "${sourceDir}/cmake/gcc-arm-none-eabi.cmake"
    },
    { "name": "Debug",   "inherits": "default", "cacheVariables": { "CMAKE_BUILD_TYPE": "Debug"   } },
    { "name": "Release", "inherits": "default", "cacheVariables": { "CMAKE_BUILD_TYPE": "Release" } }
  ],
  "buildPresets": [
    { "name": "Debug",   "configurePreset": "Debug"   },
    { "name": "Release", "configurePreset": "Release" }
  ]
}
```

Nada aquí hace referencia a Compendium. El preset funciona en cuanto
`arm-none-eabi-gcc` está en el `PATH`.

## Qué establece Compendium durante activate

Para un build embebido, el entorno exportado es mucho más pequeño que para
el flujo de trabajo de C/C++ del host. Sin vcpkg, sin flags de libc++, sin
`SDKROOT`.

| Variable                 | Valor                                                                       | Propósito                                |
| ------------------------ | --------------------------------------------------------------------------- | ---------------------------------------- |
| `CC`                     | `~/.local/compendium/languages/arm-none-eabi-gcc/<ver>/bin/arm-none-eabi-gcc` | Compilador de C                         |
| `CXX`                    | `~/.local/compendium/languages/arm-none-eabi-gcc/<ver>/bin/arm-none-eabi-g++` | Compilador de C++                       |
| `COMPENDIUM_CC_CXX_DIR`  | `~/.local/compendium/languages/arm-none-eabi-gcc/<ver>`                     | Raíz de instalación del compilador       |
| `COMPENDIUM_DEBUGGER`    | `<above>/bin/arm-none-eabi-gdb`                                            | Ruta de gdb para configurar el IDE       |
| `PATH`                   | bin del compilador, CMake, Ninja, OpenOCD                                  | Todas las herramientas accesibles desde el shell |

Esa es toda la historia embebida. El archivo de toolchain de CMake
encuentra los binarios con prefijo (`arm-none-eabi-gcc`,
`arm-none-eabi-objcopy`, etc.) en el `PATH`. Los flags del MCU vienen del
archivo de toolchain. El linker script viene de la raíz del proyecto.
Compendium solo hace que los binarios existan en versiones conocidas.

## Flashear con OpenOCD

OpenOCD viene con Compendium. Después de `cmake --build`, flashee con:

```bash
openocd \
  -f interface/stlink.cfg \
  -f target/stm32l4x.cfg \
  -c "program build/Debug/nucleo_l432kc_first.elf verify reset exit"
```

Los archivos de configuración `interface/` y `target/` vienen de dentro del
directorio de instalación de OpenOCD, que está en el `PATH` después de
activate. Cambie `stm32l4x.cfg` por la familia que coincida con su MCU.

Para depuración interactiva, ejecute OpenOCD como servidor de gdb:

```bash
openocd -f interface/stlink.cfg -f target/stm32l4x.cfg
```

Luego en otro shell:

```bash
arm-none-eabi-gdb build/Debug/nucleo_l432kc_first.elf \
  -ex "target extended-remote localhost:3333" \
  -ex "monitor reset halt" \
  -ex "load"
```

`$COMPENDIUM_DEBUGGER` apunta al mismo gdb si su IDE necesita una ruta
absoluta.

## Consideraciones

### Compendium no genera ni edita archivos de CubeMX

Compendium instala el toolchain. No genera proyectos `.ioc`, no regenera
código cuando cambia los periféricos, ni toca el archivo `.cmake` del toolchain.
CubeMX es la fuente de verdad para todo lo que está dentro de `Core/`,
`Drivers/`, `cmake/stm32cubemx/`, el linker script y el archivo de startup.
Vuelva a ejecutar CubeMX cuando cambie la configuración del hardware.

### Los flags del MCU viven en el archivo de toolchain de CMake, no en `compendium.toml`

CubeMX escribe `-mcpu`, `-mfpu`, `-mfloat-abi`, la ruta del linker script y
`--specs=nano.specs` en `cmake/gcc-arm-none-eabi.cmake`. Si necesita flags
distintos (un MCU distinto, hard vs soft float, picolibc en vez de
newlib-nano), edite ese archivo. Compendium nunca sobrescribirá estos.

Si regenera desde CubeMX después de ediciones manuales, vuelva a revisar
este archivo: CubeMX puede reescribirlo.

### vcpkg no se usa para embebidos bare-metal

vcpkg trae bibliotecas de estilo host (spdlog, fmt, gtest) que no existen en
un Cortex-M4. Deje `[packages]` fuera de `compendium.toml` para los
proyectos embebidos. Las bibliotecas embebidas (HAL, CMSIS, FreeRTOS, LVGL)
o las gestiona CubeMX o se incluyen (vendored) en el repositorio.

### `[target]` está reservado pero todavía no está conectado

La especificación de Compendium describe una tabla `[target]` para
metadatos de plataforma/arquitectura/FPU. v0.1 la parsea y emite
advertencias ante valores desconocidos, pero nada en la ruta de install o
activate la consume. No ponga la configuración del MCU en `[target]`
esperando que Compendium actúe sobre ella. Use el archivo de toolchain de
CMake.

### Los binarios gestionados por Compendium están en el `PATH`, no son alias

`which arm-none-eabi-gcc` debería resolver a una ruta bajo
`~/.local/compendium/languages/arm-none-eabi-gcc/<ver>/bin/` después de
activate. Si resuelve a `/usr/local/bin` o a una ubicación de Homebrew, o
bien se saltó activate o una instalación del sistema lo está ensombreciendo.
`compendium env` le muestra exactamente qué está exportado.

### Gatekeeper de macOS puede poner en cuarentena arm-none-eabi-gdb

La primera vez que ejecuta `arm-none-eabi-gdb` en macOS, Gatekeeper puede
bloquearlo porque el build de xPack no está notarizado por Apple. Permítalo
una vez en System Settings → Privacy & Security, o ejecute:

```bash
xattr -d com.apple.quarantine \
  ~/.local/compendium/languages/arm-none-eabi-gcc/<ver>/bin/arm-none-eabi-gdb
```

## Lista de archivos

Un proyecto STM32 listo para Compendium tiene esto en la raíz del
repositorio:

```
nucleo_l432kc_first/
├── nucleo_l432kc_first.ioc     # proyecto de CubeMX (regenerar cuando cambia el HW)
├── compendium.toml             # definición del toolchain (esto lo añade usted)
├── CMakeLists.txt              # generado por CubeMX
├── CMakePresets.json           # generado por CubeMX
├── cmake/
│   ├── gcc-arm-none-eabi.cmake # archivo de toolchain con flags del MCU
│   └── stm32cubemx/            # targets HAL/CMSIS generados
├── Core/                       # código generado + de usuario
├── Drivers/                    # HAL + CMSIS generados
├── startup_stm32l432xx.s       # startup generado
└── STM32L432XX_FLASH.ld        # linker script generado
```

Clone el repositorio, ejecute `compendium install`, haga source de activate,
compile, flashee.

## Problemas comunes

La referencia consolidada está en
[Solución de problemas](/es/reference/troubleshooting/). Para proyectos
STM32 / arm-none-eabi, los reportes más frecuentes son:

- `arm-none-eabi-gcc: command not found` — no se ejecutó `source <(compendium activate)`; compruebe `echo $CC`
- Gatekeeper de macOS bloquea `arm-none-eabi-gdb` en la primera ejecución — quite el atributo de cuarentena con `xattr -d`
- `region 'FLASH' overflowed by N bytes` — firmware demasiado grande; recorte código o edite el linker script
- `undefined reference to '_sbrk'` (y similares) — falta `--specs=nano.specs` en el archivo de toolchain
- OpenOCD `Error: open failed` — ST-Link desconectado, permisos de USB incorrectos, u otro depurador conectado
- El build toma el `gcc` del host en vez de `arm-none-eabi-gcc` — el archivo de toolchain de CMake no se aplicó

Consulte la [sección de Embebidos](/es/reference/troubleshooting/#embebidos-arm-none-eabi)
para las soluciones.
